# Проектирование архитектуры программных систем

**Студент:** Киров Дмитрий Владимирович  
**Группа:** РИС-23-3  
**Вариант:** индивидуальная тема ВКР «Разработка системы для повышения эффективности пользовательских интерфейсов информационных систем на основе прогнозирования зрительного внимания и аффордансной разметки».

## Постановка задачи

Необходимо спроектировать веб-приложение для предварительного анализа интерфейсов по скриншотам. Пользователь загружает изображение и указывает тип интерфейса. Система выделяет элементы, прогнозирует распределение зрительного внимания и оценивает воспринимаемые аффордансы: какие действия предполагает внешний вид элемента, включая нажатие, ввод текста, прокрутку и перетаскивание. При наличии дополнительных сведений о функциях элементов система сопоставляет их с воспринимаемыми действиями. По результатам анализа она выявляет потенциальные проблемы по правилам и формирует рекомендации с пояснениями.

**Пользователи:** UX/UI-дизайнеры и аналитики, владельцы анализируемых интерфейсов, исследователь-разработчик. Каждая роль запускает анализ в собственной сессии. Описания областей вносит тот, кто загружает скриншот. Исследователь также работает с подсистемой подготовки данных, моделей и правил.

## Требования к системе

1. Загрузка одного скриншота в PNG или JPEG с проверкой входа (FR-01, FR-04).
2. Выбор типа интерфейса — веб, десктопный или мобильный (FR-02).
3. Запуск анализа и получение результата либо причины ошибки (FR-03, FR-11).
4. Выделение элементов и определение их границ (FR-05).
5. Построение прогнозной карты внимания и расчёт оценок по элементам (FR-06, FR-07).
6. Оценка воспринимаемых действий с указанием недостаточной уверенности (FR-08).
7. Приём описаний функций с источником и статусом проверки поведения (FR-13).
8. Подтверждение рамки в готовом отчёте, сопоставление описания с действиями и повторная проверка по сохранённым оценкам (FR-20, FR-14, FR-09, FR-10).
9. Выявление потенциальных проблем по заданным правилам (FR-09).
10. Формирование рекомендаций с указанием элемента, причины и предлагаемого изменения (FR-10).
11. Просмотр карты, разметки, пояснений и предупреждений о применимости модели (FR-11).
12. Выгрузка отчёта в JSON (FR-12).
13. Подготовка версионируемых наборов, обучение моделей и отдельная итоговая оценка (FR-15, FR-16, FR-17).
14. Публикация выпуска моделей и версий правил для новых задач (FR-18, FR-19).

Подробные требования, приоритеты и критерии проверки приведены в [лабораторной работе № 1](./Lab%20Work%20%E2%84%961/docs/LAB_1_REPORT.md).

## Дополнительный контекст

Система помогает выбрать элементы для проверки или доработки ещё до пользовательского тестирования. При анализе только скриншота пользователь получает прогнозы. Для вывода о расхождении с назначением элемента нужны описание функции и подтверждённая рамка.

## Архитектурные границы

Система включает фронтенд, бэкенд и отдельный ML-сервис. Фронтенд обеспечивает взаимодействие с пользователем, бэкенд организует запросы анализа и формирует отчёт, ML-сервис выполняет прогнозы моделей через API. Модуль рекомендаций применяет базу правил к оценкам внимания, аффордансов и дополнительным сведениям.

Исследователь размечает учебные изображения в отдельном локальном инструменте и экспортирует разметку в файл. В контуре подготовки CLI импортирует и проверяет эти данные, фиксирует разбиение и проводит обучение. Детектор, параметры моделей и пороги выбирают на validation. Набор test используют для итоговой оценки зафиксированной конфигурации. Опубликованный выпуск содержит детектор, модель внимания, модель аффордансов и настройки предобработки. Версия правил хранится отдельно.

## Ограничения предметной области

Прогноз внимания не является измерением движений глаз конкретного человека. Аффорданс описывает действие, предполагаемое по внешнему виду элемента; фактическое поведение элемента и намерение пользователя по скриншоту не устанавливаются. Несколько воспринимаемых действий могут относиться к одному элементу.

Дополнительные сведения могут основываться на описании пользователя, DOM, дереве Accessibility или коде. Источник и статус проверки поведения сохраняются в отчёте. Недостаточная уверенность модели обозначает ограничение анализа и не считается самостоятельной проблемой юзабилити. Рекомендации требуют проверки, а повышение эффективности интерфейса после изменений оценивается отдельно.
